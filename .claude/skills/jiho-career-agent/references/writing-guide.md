# 글쓰기와 사실 기준

## 말투

- 겸손하되 실제로 한 일은 동사로 분명하게 쓴다. "참여했습니다"로 뭉개지 말고 무엇을 작성·정리·확인·수정했는지 쓴다.
- 과장된 전문가 페르소나, 딱딱한 기술 매뉴얼, 거창한 추상어("혁신", "패러다임", "시너지", "극대화", "최고의")는 쓰지 않는다.
- 소제목은 문장형으로 자연스럽게, 그 문단에서 실제로 한 일을 담는다. ("~을 직접 만들었습니다", "~을 보고 고쳤습니다")
- 합격을 보장하는 말 대신 읽는 사람이 역할·기여·검증을 판단할 수 있게 쓴다.
- 경력 방향(국비과정 때 느낀 강점 → 먼저 엔지니어로 입사 → 학위·자격 병행)은 필요할 때 한두 문장으로만 쓰고 자기비하로 쓰지 않는다.
- 공고에서 묻지 않으면 퇴사 사유·공백기를 일반 자소서에 쓰지 않는다. 공백기에 했다는 일을 새로 만들지 않는다.

## 분량

- 문항·글자 수 제한이 있으면 그것이 우선이다. 공백 포함/제외 기준을 공고에서 확인하고, 모르면 둘 다 보고한다.
- 제한이 없으면 기본본 정도(공백 포함 약 2,000~3,000자)를 쓴다.
- 보통 소제목 4~5개, 소제목마다 한 문단(4~7문장).

## 기본본을 다루는 방식

1. 흐름은 기본본을 유지한다. 공고에 맞춰 순서를 바꾸고, 문장을 보강하고, 공고 업무와 연결하는 문장을 더한다.
2. 해커톤(한끗)은 기존 경력에 **더하는 경험**이다. 첫 소제목이나 글 전체의 주인공으로 만들지 않는다. 한 소제목 이내.
3. AX 흐름: 반복 업무 문제의식 → 실무 경력 → 직접 만든 도구와 검증 → (해커톤) → 입사 후 할 일.
4. 온보딩·기술지원 흐름: 사용자 교육 → 질문을 개발자와 연결 → 기술지원 기초 → (해커톤 사용자 행동 개선) → 개인 프로젝트와 입사 후 할 일.
5. 공고가 둘 다에 걸치거나 사용자가 둘 다 요청하면 두 패킷을 따로 만든다.

## 사실 기준 (가장 중요)

- 모든 문단은 `references/profile.json`의 fact ID를 근거로 가진다. 근거 없는 사건·수치·기관명은 쓰지 않는다.
- 사용자 문답(conversation), 이력서(resume), 저장소 구현(personal/hackathon), 추정, 앞으로의 계획을 구분한다. 계획은 "~하겠습니다"로만 쓴다.
- 과거에 "그럴싸하게 꾸며 달라"고 한 요청이 있었더라도 그것은 사건이 실제 있었다는 근거가 아니다.
- 웹에서 찾은 다른 기관 사례는 참고 아이디어일 뿐 지원자가 벤치마킹했다는 증거가 아니다.
- 저장소에 있는 기술 = 지원자가 모두 수작업 코딩했거나 상용 운영했다는 뜻이 아니다. 개인 프로젝트는 "AI를 활용해 기획·설계·구현·검증을 혼자 진행"으로 쓴다.
- 실무 경력 / 개인 학습 프로젝트 / 팀 프로젝트 / 가상 시연을 섞지 않는다.

## AI가 쓴 티가 나지 않게 (2026-11-26 사용자 요청)

읽는 사람이 "AI가 썼다"고 느끼는 신호를 지운다. 사실을 꾸며 내라는 뜻이 아니다. 확인된 사실만 쓰되 사람이 쓴 글처럼 쓴다.

- **공식처럼 반복되는 문장 금지**: "~가 제가 해 온 일과 가장 가깝다고 생각해 지원했습니다", "~라는 것을 배웠습니다", "~하겠습니다"로 모든 문단을 닫지 않는다. 배운 점은 글 전체에서 한두 번만 쓴다.
- **문단 모양을 다르게**: 모든 문단이 "경험 → 결과 → 교훈" 순서면 AI 티가 난다. 어떤 문단은 장면(그때 무엇이 문제였는지)으로 시작하고, 어떤 문단은 짧게 끝낸다. 문장 길이도 섞는다.
- **나열 줄이기**: "A와 B, C와 D·E 작성"처럼 명사를 줄줄이 잇지 않는다. 꼭 필요한 두세 개만 고르고 나머지는 빼거나 포트폴리오에 맡긴다. 가운뎃점(·)은 한 문장에 하나 정도.
- **추상어 대신 실제 상황**: "흐름", "지점", "기준", "역량" 같은 말 대신 실제로 있었던 일(질문이 쏟아졌다, 보고서를 먼저 내 버렸다, 출처 번호가 원문과 달랐다)을 쓴다. 단, 없던 장면·대사·감정은 지어내지 않는다.
- **소제목도 평범하게**: 소제목이 전부 "~했습니다"로 끝나는 같은 모양이면 바꾼다. 짧은 명사형, 질문형, 인용형을 섞어도 된다.
- **사람 말투**: "솔직히", "그래서", "그런데"처럼 생각이 이어지는 접속을 쓰되 과하지 않게. 번역투("~을 통해", "~에 있어서", "~함에 있어")와 과한 존댓말 겹침을 피한다.
- **회사마다 같은 문단 재사용 금지**: 같은 사실이라도 회사 톤과 직무에 맞게 다시 쓴다.

- "이 지원서도 AI(제가 만든 에이전트)로 썼다"처럼 **이 글을 AI가 썼다는 문장은 쓰지 않는다**(2026-11-26 사용자 결정). 읽는 사람이 진정성을 깎아 읽는다.
  - AI 직무라면 도구는 직접 만든 프로젝트로 설명한다. 예: "지원 준비에 직접 만든 지원서 에이전트를 쓰고 있습니다", 그리고 무엇을 정했고 무엇을 검사하게 했는지.
  - AI가 핵심이 아닌 직무는 도구 언급을 한 문단 이하로 줄인다.
  - 스토리 초안이 있으면 도구를 "확인된 사실만 쓴다"고 소개하는 문장과 ⟦ ⟧ 장면이 서로 어긋나지 않는지 보고 때 짚어 준다.

## 문항마다 반론·우려에 답한다 (2026-11-26 사용자 요청)

- 문항(소제목) 하나는 채용 담당자가 이 지원자에게 품을 반론·우려 하나를 다룬다. 예: "비전공·짧은 경력인데 정말 만들 수 있나", "AI 결과가 틀리면 사고가 나지 않나", "도메인(제조·리테일) 경험이 없다", "필수 요건 미충족", "사내 보안·권한 경험 없음".
- 구성: 우려를 먼저 짧게 인정하거나 짚고 → 확인된 경험(근거)으로 답하고 → 입사 후 구체적인 해결책·계획으로 닫는다.
- 우려를 짚는 말투는 문항마다 바꾼다("의심하실 수 있습니다"만 반복하지 않기). 첫 문단은 '첫 문단 각도' 규칙을 우선한다.
- 해결책은 측정 가능한 행동으로 쓴다(첫 주에 무엇을, 어떤 검사·승인 단계를, 무엇을 공개해 확인받을지). 약속은 지킬 수 있는 범위만.
- **분량: 문항(본문)당 공백 포함 500~700자.** 제한이 없으면 문항 4개(약 2,000~2,800자)를 기본으로 한다. 공고·문항에 글자 수 제한이 있으면 그것이 우선이다. `check`가 범위를 벗어난 문항을 경고한다(`meta.limits.section_chars`로 조정, null이면 끔).

## 첫 문단은 그 회사만을 위한 한 가지 각도 (2026-11-26 사용자 피드백)

경력을 시간순으로 늘어놓은 글은 채용 담당자에게 혹하지 않는다(헬로월드랩스 v1 반려).

- 첫 문단은 '이 회사 사업·공고 문장 ↔ 내 경험'이 딱 맞물리는 한 가지 각도로 연다. 예: 교육 회사 → "가르쳐 본 사람이자 지금 배우는 사람", 자격요건이 한 줄인 공고 → 그 문장을 인용하고 바로 답하기, 고문서 디지털화 회사 → 문화유산 기관 문서 이관 경험.
- 공고의 핵심 문장 하나를 인용하고 "그게 제가 해 온 일"로 받는 구성은 효과가 좋다. 단, 문단마다 반복하지 않는다(한두 번).
- 회사 숫자와 내 숫자를 나란히 쓸 때는 각각 무엇의 수인지 분명히 하고, 검사에 걸리면 회사 쪽은 다른 표현(매장 수 등)으로 바꾼다.
- 경력 나열은 둘째 문단 이후로 미루고, 각 문단도 공고 업무 하나에 답하는 형태로 쓴다.

## 대충 쓰지 않는다 (2026-11-26 사용자 피드백: 제이알인더스트리 v2 "너무 부실, 해커톤 빠짐")

초안을 내기 전에 아래를 모두 확인한다. 하나라도 빠지면 고친 뒤 낸다.

- **공고 업무·자격 문장 하나하나에 답했는가.** 공고의 업무(duties)와 필수 요건마다 그 문장에 답하는 문항이나 문장이 있어야 한다. 특히 둘째·셋째 업무처럼 눈에 덜 띄는 항목을 빠뜨리지 않는다(예: '팀별 업무 데이터를 AI가 쓸 수 있게 정리' → 사실 데이터 파일 설계 경험).
- **관련 있는 근거를 다 썼는가.** profile.json의 사실 중 이 공고와 이어지는 것을 먼저 전부 뽑아 놓고 고른다. 대표 프로젝트 하나만 반복하지 말고, 직접 만든 도구가 여럿이면 이름과 하는 일을 구체적으로 나열한다.
- **해커톤을 빠뜨리지 않았는가.** AI·개발·기획·PM·QA 계열 공고에는 해커톤(팀장, PRD·기능명세서, AI 추출과 규칙·코드 분리, 계산 엔진 시험 172건 재실행, Clarity 기반 UX 수정)을 한 문항으로 넣는다. 첫 문항의 주인공으로는 두지 않는다. '팀으로 마감 안에 완성' 같은 우려(혼자 만든 도구뿐 아닌가)에 답하는 자리로 쓴다.
- **문항이 구체적인가.** 문항마다 고유명사(회사·사업·도구·기술), 내가 한 행동, 확인 방법(검사·시험·기록), 회사 업무로의 연결이 들어 있어야 한다. "~하겠습니다"만 있는 문단은 다시 쓴다.
- **분량.** 문항당 500~700자를 채우되 채우기용 문장은 넣지 않는다. 재료가 충분하면 문항 5개까지 쓴다.
- **다시 읽기.** 다 쓴 뒤 채용 담당자 입장에서 "이 사람만 쓸 수 있는 글인가, 다른 지원자도 쓸 수 있는 글인가"를 묻고, 후자면 고친다.

## 회사 톤앤매너 맞추기

1단계 기업 조사에서 회사가 스스로 쓰는 말투를 확인해 `meta.tone`에 적는다(근거 출처 포함).

- 스타트업·수평 문화·실무 위주 공고(짧은 문장, 구어체 공고): 문장을 짧게, 결과물과 숫자 위주로, 격식 표현을 줄인다.
- 제조·중견 기업, 헤드헌터 경유 공고: 차분하고 정확하게. 업무 범위와 기간, 다룬 시스템을 분명히 쓰고 감성 표현을 줄인다.
- 교육·컨설팅 회사: 사람을 가르치고 설득한 장면을 앞에 두고, 듣는 사람 입장의 표현을 쓴다.
- 공고가 직접 요구한 형식(예: "3줄 설명", "질문을 던진 이유")이 있으면 그 형식을 그대로 따른다.

## 소제목 (2026-11-26 사용자 요청)

채용 담당자가 소제목만 훑어도 "이 사람은 이런 일을 해 봤구나"가 보이게 쓴다.

- 그 문단의 첫 장면이나 핵심 주장을 소제목으로 끌어올린다. 예: "떠나려는 사람의 이유부터 듣습니다", "계산은 AI가 아니라 규칙에 맡겼습니다".
- "~하는 일", "~에 대하여", "DB와 API"처럼 설명형·명사 나열형 소제목은 쓰지 않는다.
- 공고에서 강조한 표현(사람·소통, 검증, 요구사항 등)을 소제목에 녹인다.
- 약점 문단도 "처음입니다"로 끝내지 말고 대안을 붙인다. 예: "채용은 처음이지만, 사람을 잇는 일은 처음이 아닙니다".

## 스토리 초안 (2026-11-26 사용자 요청)

사용자는 합격할 만한 스토리를 넣은 버전을 받아 자기 경험에 맞게 직접 첨삭한다.

- 사실만으로 쓴 `자기소개서.txt`(검사 통과본)는 그대로 두고, 같은 폴더에 `자기소개서_스토리초안.txt`를 따로 만든다. 맨 위에 "⟦ ⟧ 안은 예시 장면이니 실제 경험으로 바꾸거나 지운 뒤 제출" 안내를 둔다.
- 지어낸 장면은 문단마다 하나 정도, 반드시 ⟦ ⟧로 감싼다. 괄호 밖은 확인된 사실만 쓴다.
- 장면에도 수치(몇 %, 몇 건 감소)·회사명·자격·직함은 지어내지 않는다. 실제 경력과 같은 회사·업무 안에서 있었을 법한 장면으로만 쓴다.
- 보고할 때 스토리 초안 전문을 채팅에 적고, 회사별로 넣은 장면 목록을 따로 정리한다.
- 공개 포트폴리오에는 스토리 장면을 넣지 않는다.

## 이력서 제목

채용 담당자는 지원자 목록에서 제목만 몇 초 보고 이력서를 열지 정한다. 희망을 늘어놓지 말고 **이 직무에 맞는 근거**를 먼저 보여 준다.

- 형식: `[가장 강한 근거 1~2개] + [공고 직무명] + 김지호`. 근거는 숫자와 맥락이 함께 있는 실적(예: 300명 대면 교육)이나 직접 만든 결과물(예: Claude Code 스킬·훅, AI 에이전트)로 쓴다.
- 길이: 45~60자. 근거 두 개는 '+'나 '·'로 묶고, 쉼표 뒤에 직무에서 할 일을 짧게 붙인다.
- 근거는 공고 필수 요건이나 핵심 업무와 바로 이어지는 것으로 고른다. 공고마다 순서를 바꾼다.
- 피할 것: "~하고 싶은 김지호입니다"처럼 희망만 있는 제목, "열정", "인재", "전문가", "최고" 같은 자기평가, 맥락 없는 숫자, 확인되지 않은 경력(PL·PM 총괄 등).
- 예: `300명 대면 교육 운영 + Claude Code 업무 자동화, 고객 문제를 끝까지 챙기는 AX PM 김지호`
- 공고가 원하는 사람으로 바로 읽히는 한 구절을 넣는다(예: "개발자와 말이 통하는", "AI가 틀린 곳을 잡아내는"). 공고가 신입을 우대하면 "신입"을 약점이 아니라 맞춤 조건으로 쓴다.
- 지원서 제목에는 ⟦ ⟧ 예시 장면을 쓰지 않는다.
