# AI 에이전트의 사람 승인 지점, 어디에 둘까

> 시리즈: 금융 고객에게 설명하는 AI 도입 (2)

결론부터 말씀드리면, AI 에이전트의 승인 지점은 업무 종류가 아니라 작업의 결과로 정해야 합니다. 하지만, 모든 작업에 승인을 걸어버리면 승인은 금방 형식이 됩니다. 그러니, 승인을 둘 곳과 뺄 곳을 함께 정하셔야 합니다.

## 에이전트와 승인 지점

AI 에이전트란, 사람의 요청을 받아 여러 단계의 작업을 스스로 실행하는 AI 프로그램을 말합니다. 즉, 답만 하는 것이 아니라 메일을 보내고, 티켓을 만들고, 설정을 바꾸는 데까지 간다는 뜻이죠.

금융보안원은 2026년 10월 8일 「금융분야 AI 에이전트 보안 평가기준」을 발표하면서, 에이전트는 판단에 그치지 않고 실행까지 하기 때문에 위협이 실제 행위로 이어질 수 있다고 설명했습니다.[B8]

여기서 승인 지점이란, 에이전트가 작업을 실행하기 직전에 사람이 확인하는 자리를 말합니다. 즉, "실행 버튼을 누가 누르느냐"입니다.

## 바뀌는 질문 하나

제가 보기에, 에이전트가 들어오면 금융 고객의 질문은 하나로 모입니다. "에이전트가 혼자 끝내도 되는 일과 사람이 승인해야 하는 일을 어디서 나누느냐"라는 질문입니다.

지금까지의 질문은 "AI가 판단해도 되느냐"에 가까웠습니다. 2026년 6월 22일 시행된 「금융분야 인공지능 가이드라인」도 현 단계에서 AI는 업무의 보조수단이고, 최종 의사결정과 책임은 임직원에게 있다는 원칙을 두고 있습니다.[B4][B9]

하지만, 에이전트는 하루에도 수많은 작업을 실행합니다. 모든 작업 하나하나를 "최종 의사결정"으로 볼 수는 없죠. 가이드라인이 어떤 상황에서 사람의 개입을 요구하는지, 세부 기준은 원문으로 확인하지 못했습니다. [확인 필요: X14]

그러니, 원칙을 실제 시스템에 옮기려면 "어떤 작업 앞에 사람을 세울 것인가"를 먼저 정해야 한다고 볼 수 있습니다.

## 결과로 나눈다

제가 생각했을 때, 승인 지점을 나누는 가장 실무적인 기준은 작업의 결과입니다. 아래 세 가지 중 하나라도 해당하면 사람 승인을 두고, 셋 다 아니면 자동으로 실행하되 기록을 남기는 방식이죠.

| 기준 | 작업 예 | 처리 |
|---|---|---|
| 되돌릴 수 없는가 | 삭제, 덮어쓰기 | 사람 승인 |
| 회사 밖으로 나가는가 | 외부 메일, 외부 공유 | 사람 승인 |
| 돈이나 권한이 움직이는가 | 결제, 권한 변경 | 사람 승인 |
| 셋 다 아님 | 조회, 초안 작성, 내부 티켓 | 자동 실행 + 기록 |

참고로, AWS가 Amazon Quick의 스마트 승인 기능에서 사람에게 넘기는 작업도 외부 전송, 권한 변경, 삭제·덮어쓰기, 결제입니다.[A10] 위 세 가지 기준과 거의 겹치는 셈이죠.

가상의 사례로 풀어보겠습니다. 가상의 보험사 B가 IT 운영 에이전트를 도입한다고 해보겠습니다. 장애 로그 조회와 장애 티켓 작성은 자동으로 실행합니다. 하지만, 서버 설정 변경은 되돌리기 어렵고, 사용자 권한 부여는 권한이 움직이는 작업이니 사람 승인을 둡니다. 즉, 같은 에이전트 안에서도 작업마다 처리 방식이 달라지는 것입니다.

## 승인이 너무 많으면

반대로, 불안하다고 모든 작업에 승인을 걸어버리면 다른 문제가 생깁니다.

금융보안원의 평가기준에는 사람이 승인하는 체계를 갖추는 항목과 함께, 승인 요청이 과도해 담당자에게 부담이 쏠리는 상황을 막는 항목이 들어 있습니다.[B8] 즉, 승인을 많이 거는 것 자체가 위험 요인으로 다뤄진다는 뜻이죠.

예를 들면, 담당자 한 명에게 하루에 수십, 수백 건의 승인 요청이 쌓이면, 내용을 제대로 보지 않고 승인 버튼만 누르는 상황이 오게 됩니다. 아무리 승인 절차를 촘촘하게 만들어도, 사람이 내용을 보지 않으면 소용이 없죠.

그러니, 승인 지점을 정할 때는 "어디에 둘까"와 함께 "어디에서 뺄까"를 같이 정해야 합니다.

## 승인을 시스템에 남긴다

승인 지점은 사람의 기억이나 업무 매뉴얼이 아니라, 시스템 설정으로 고정해두는 편이 안전합니다.

예를 들면, Amazon Bedrock Agents는 함수마다 "실행 전 사용자 확인"을 켤 수 있습니다.[A12] 켜지 않으면 확인 없이 실행되니, 함수를 만들 때마다 따로 정해줘야 하죠.[A12] AWS 문서는 이 설정이 악의적인 프롬프트 주입으로 작업이 실행되는 것을 막는 데 도움이 될 수 있다고 설명합니다.[A12]

또한, Amazon Bedrock AgentCore의 Policy 기능은 에이전트 코드 바깥에서, 에이전트가 도구를 호출할 때마다 정책으로 허용과 거부를 판단합니다.[A13][A14] 기본값은 거부이고, 같은 세션에서 사전 승인이 있었는지, 누적 금액이 한도를 넘었는지 같은 조건도 걸 수 있습니다.[A14] 이 기능은 2026년 3월 정식 출시됐고, 서울 리전에서도 쓸 수 있습니다.[A13]

물론, 자동 승인 기능도 있습니다. 하지만, AWS도 Quick 문서에서 자동 검토가 정책을 대신하지 않으며, 반드시 사람이 승인해야 하는 작업은 권한 설정으로 고정하라고 안내합니다.[A10] 또한, 자동 승인 기록이 남았다고 해서 그 작업이 실제로 실행됐다는 뜻은 아니라고 밝히고 있습니다.[A10] 즉, 승인 기록과 실행 기록은 따로 봐야 하는 것이죠.

## 도입 전에 확인할 항목

에이전트 도입을 검토하신다면, 아래 사항을 먼저 정리해두셔야 합니다.

1. 에이전트의 작업 목록을 만든다.
에이전트 단위가 아니라, 에이전트가 호출하는 도구와 함수 단위로 목록을 만드셔야 합니다. 승인 설정이 함수와 도구 단위로 걸리기 때문이죠.[A12][A14]

2. 작업마다 세 가지 질문을 붙인다.
되돌릴 수 있는지, 회사 밖으로 나가는지, 돈이나 권한이 움직이는지를 표에 적어두시면 됩니다. 하나라도 해당하면 사람 승인 후보입니다.

3. 사람 승인은 정책으로 고정한다.
반드시 사람이 승인해야 하는 작업은 자동 판단에 맡기지 마시고, 권한과 정책 설정으로 고정해두셔야 합니다.[A10]

4. 승인 건수를 잰다.
시범 운영 기간 동안 담당자별 하루 승인 건수를 기록해두셔야 합니다. 건수가 과도하면, 승인 지점을 줄이거나 담당자를 나누는 조정이 필요합니다.[B8]

5. 승인 기록과 실행 기록을 함께 남긴다.
누가 언제 승인했는지와, 그 작업이 실제로 실행됐는지를 따로 확인할 수 있어야 합니다.[A10]

## 지금 할 일과 기다릴 일

**지금 검토해볼 만한 경우**

- 조회, 초안 작성, 내부 티켓처럼 결과가 회사 안에 머무는 작업이 대부분인 에이전트입니다. 예를 들면, IT 운영이나 내부 문서 업무죠.
- 이미 권한 체계가 정리되어 있어서, 에이전트 작업을 기존 권한에 연결하기 쉬운 경우입니다.

**기다리는 편이 나은 경우**

- 신용평가나 대출 심사처럼, 고객의 금융거래에 직접 영향을 주는 판단에 에이전트를 쓰려는 경우입니다. AI 기본법의 고영향 AI 규정과 가이드라인의 세부 기준을 먼저 확인해야 합니다. [확인 필요: X15]
- 금융보안원 평가기준의 결과를 보고 승인 체계를 설계하고 싶은 경우입니다. 금융보안원은 올해 말까지 시범 검증을 거쳐 2027년부터 정식 점검기준으로 쓸 계획이라고 밝혔습니다.[B8] 다만, 이것은 계획이지 확정된 일정이 아닙니다.

이 글은 개인이 공개 자료를 바탕으로 작성한 비공식 분석이며, 솔트웨어의 공식 입장이 아닙니다. 법률 자문이 아니며, 규제 충족이나 감사 통과를 보장하지 않습니다. 글에 나온 보험사 B는 가상의 사례입니다. 초안 작성에 AI 도구를 활용했고, 작성자가 내용을 검토합니다. 작성 기준일은 2026년 11월 3일이며, 클라우드 서비스와 규제는 이후 바뀔 수 있습니다.
