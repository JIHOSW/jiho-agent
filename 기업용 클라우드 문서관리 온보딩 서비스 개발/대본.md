# FIRSTMILE 발표·시연 대본

소요 시간은 약 4~5분입니다. 화면 전환과 실제 낭독 속도에 따라 조절합니다.

**체험 링크:** https://firstmile-onboarding-1104.day1companyk-6083.chatgpt.site/

이 대본은 현재 가상 데이터·규칙 기반 데모를 기준으로 작성했습니다. 실제 AI나 운영 시스템이 연결된 것처럼 설명하지 않습니다.

## 1. 소개와 기획 배경 · 약 40초

**화면:** 온보딩 현황

> 안녕하세요. 고객이 서비스를 도입한 뒤 첫 업무를 완료할 때까지 지원하는 온보딩 도구, FIRSTMILE을 소개하겠습니다.
>
> 저는 시스템 운영과 기술 문의 대응, 사업관리 과정의 요청 정리·개발자 협의·테스트·검수, 사용자 교육을 경험했습니다. 이 과정에서 기술을 이해하는 것만큼 고객의 상황을 파악하고 이해할 수 있게 설명한 뒤 결과까지 확인하는 일이 중요하다고 느꼈습니다.
>
> 이 경험을 바탕으로 고객 현황, 원인 확인, 안내문, 후속 작업을 한 흐름으로 연결했습니다. 구현에는 AI 코딩 도구의 도움을 받았습니다.

## 2. 어떤 솔루션의 온보딩인가 · 약 35초

**화면:** 전체 프로세스 또는 프로젝트 소개

> 기업에 문서 등록·공유·검색·권한·버전관리 기능이 있는 클라우드 문서관리 서비스를 제공한 상황을 가정했습니다. 특정 회사의 실제 제품은 아닙니다.
>
> FIRSTMILE은 문서관리 제품 자체가 아니라 공급사 온보딩 담당자의 내부 도구입니다. 고객 등록과 목표 합의, 초기 설정, 문서 이관, 사용자 교육, 첫 활용 확인, 운영 인계를 지원합니다.
>
> 완료 기준은 설치나 교육 참석만이 아니라, 고객이 합의한 실제 업무를 수행했는지로 설정했습니다.

## 3. 고객 현황과 고객 등록 · 약 35초

**화면:** 고객 현황 → 고객 추가

> 고객별로 담당자와 첫 활용 목표, 현재 단계, 먼저 확인할 상황을 볼 수 있습니다. 고객 추가에서는 회사명, 담당자, 사용 인원, 도입일과 목표일, 첫 활용 목표를 등록합니다.
>
> 예를 들어 ‘제안서 한 건을 게시하고 팀원 두 명이 검색하고 열람한다’처럼 관찰 가능한 목표를 정합니다.
>
> 새 고객은 사용 기록이 없으므로 0%와 자료 확인 필요 상태로 시작합니다. 등록만 했는데 시스템 로그가 생기거나 문제가 확정되도록 만들지 않았습니다.

시연 시간이 짧으면 폼만 보여주고 닫습니다. 직접 등록할 경우 가상의 회사명과 담당자를 사용합니다.

## 4. 원인을 어떻게 확인하는가 · 약 70초

**화면:** 모노랩 기본 기록 → 근거 숫자 클릭

> 모노랩은 ‘문서를 저장했는데 동료가 검색할 수 없다’고 문의한 사례입니다.
>
> 여기서는 같은 문서의 현재 상태가 DRAFT이고 게시 기록이 없다는 샘플 기록을 제공합니다. 제품 가이드에는 임시 저장 문서는 작성자만 볼 수 있고, 게시해야 공유된다고 정의했습니다. 이 두 자료를 대조해 게시 여부를 먼저 확인하도록 제안합니다.
>
> 지금 화면의 시스템 기록은 제가 구성한 가상 자료입니다. 실제 서버에서 자동으로 가져온 로그가 아닙니다.

**조작:** 시연 기록을 ‘게시 후 검색 오류’로 변경

> 게시 완료 이후 색인 실패 기록으로 바꾸면 조치도 개발 담당자에게 오류를 전달하는 방향으로 달라집니다.

**조작:** ‘기록 부족’, ‘기록 충돌’로 변경

> 기록이 부족하거나 서로 다르면 원인을 확정하지 않고 추가 확인을 요청합니다. 게시 이벤트가 보이지 않는다는 사실만으로 미게시라고 단정해서는 안 됩니다.
>
> 실제 서비스에 적용하려면 문서 상태 API, 권한 정보, 로그 수집 기간과 검색 색인 상태를 연결해야 합니다. AI API 연결과 업무 시스템 연결은 별개의 작업입니다.

## 5. 고객 안내와 후속 실행 · 약 50초

**화면:** 기본 기록으로 복귀 → 안내문 초안 보기 → 작업 등록

> 확인한 내용은 고객 안내문 초안으로 이어집니다. 담당자가 근거와 표현을 검토하고 수정한 뒤 복사하도록 했으며, 고객에게 자동 발송하지 않습니다.
>
> 다음 행동은 담당자와 기한을 지정해 작업으로 등록할 수 있습니다. 안내를 보냈다는 사실에서 끝나지 않고 고객이 재시도했는지, 실제로 사용할 수 있게 됐는지를 후속 확인하는 흐름입니다.
>
> 작업 완료와 고객 온보딩 단계 완료는 별개입니다. 실제 확인 근거 없이 고객 진행률을 자동으로 올리지는 않습니다.

## 6. 현재 범위와 향후 검증 · 약 40초

**화면:** AI 연결 안내 또는 프로젝트 소개

> 현재 공개 버전은 가상 데이터와 규칙 기반 분석입니다. 실제 AI를 호출하는 서버 코드와 근거 ID·응답 형식 검증은 준비했지만, API 키가 없어 실제 응답 품질은 아직 검증하지 않았습니다.
>
> 고객과 작업은 방문자 본인의 브라우저에 저장되며 공유 DB나 실시간 CRM과 연결되어 있지 않습니다.
>
> 앞으로는 실제 AI 응답의 원인 판단, 문서 해석, 질문과 안내문의 적절성을 평가하고, 이후 업무 시스템의 읽기 전용 연동과 사용자 피드백을 검토하려고 합니다. 자동 테스트와 실제 업무 품질 평가는 구분해서 진행하겠습니다.

## 면접 질문에 답할 때

**본인이 기여한 부분은 무엇인가요?**

> 운영·사업관리·교육 경험을 바탕으로 문제와 요구사항을 정리하고, 고객 시나리오와 완료 기준, 담당자의 검토·후속 실행 흐름을 설계했습니다. 구현에는 AI 코딩 도구를 활용했고, 결과를 테스트와 시연으로 확인했습니다.

**어떤 실제 경험이 반영됐나요?**

> Linux·Oracle 운영과 기술 문의 대응, PL·PMO의 요청 정리·개발자 협의·검수 경험을 반영했습니다. 약 300명 대상 사용자 교육과 44장 교육자료·발표 대본 작성 경험은 고객 안내와 교육 준비 흐름에 연결했습니다.

**성과는 무엇인가요?**

> 현재는 업무 흐름을 구현하고 기능을 검증한 단계입니다. 실제 고객의 업무 시간 단축이나 도입 성공률 개선은 측정하지 않았습니다. 교육 당시 피드백도 구두 반응과 고객 담당자를 통한 긍정적 피드백 수준으로 설명하고 있습니다.
